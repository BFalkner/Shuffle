How the simulator works

This page follows one routine from the moment you pick it in the simulator to the scores on the screen. Each section has its own diagram. Click a diagram to see it full size, and press Escape or click again to close it.

The code has no classes. It has two kinds of things. The first is plain data: a deck is a list of card numbers, top card first, and a routine is a list of move names such as ["mash", "mash", "pile"]. The second is functions that take data and return new data. mash(deck) returns a new, shuffled deck and leaves the old one alone. Each file holds the functions for one step, so the files read like chapters. If you think in classes, treat a file such as moves.ts as a class with only static methods. The five metrics are the nearest thing to objects: each is a small object with the same fields, like five classes that implement one interface.

All engine files are in src/engine/ and all simulator page files are in src/pages/Simulator/. The diagrams give paths from src/.

1The page keeps your routines

The simulator calls a saved routine an experiment. An experiment has an id, a seq (the list of moves), and a name only if you typed one. Without a name, the page calls the experiment by its moves in notation, so the name follows every edit. The page loads the list from your browser's localStorage when it opens and writes it back after every change. If nothing is saved, it starts from the defaults in experiments.ts. A list saved before the defaults last changed gets any new default added, and keeps everything it had.

One experiment is active: the one open in the editor. Every edit changes it at once. useRoutineEditor keeps an undo history for each experiment and a caret, the place between moves where the next move goes in. Moves can also be dragged: within the strip to reorder them, off it (anywhere else on the page) to take them out, and from a move button into it to add one. MoveStrip.tsx handles those drags with React Aria's drag and drop, and each one is a single undoable change. The page also holds the deck you chose (its kind and size) and which other experiments are drawn on the charts. It deals one starting deck for the example deck under the editor. That deck is only for the example. The measurements deal their own decks in section 4.

Files: pages/Simulator/Simulator.tsx, pages/Simulator/experiments.ts, pages/Simulator/useRoutineEditor.ts, pages/Simulator/MoveStrip.tsx

2Web workers compute the results

One experiment takes 1,200 decks through every step of its routine. That runs in a pool of web workers, one per spare processor core and at most four, so the page keeps responding while you edit. On every render the page lists what it wants scored, most important first: the active experiment, then the ones on the charts, then the rest, all from the current starting deck, then the same again from the other deck. Each idle worker takes the first job that is neither scored nor already in progress.

Each job seeds the random numbers from its own key, so a routine gets the same score in every worker and on every visit. Undoing an edit brings back exactly the numbers it had. Finished results go into a cache that lasts until you reload the page. The cache key is the deck kind, the deck size, and the moves. Two experiments with the same moves share a result, and switching decks back and forth costs nothing.

While an edit is being scored, each experiment keeps showing the last result that arrived for it, dimmed, so the page never goes blank.

Files: pages/Simulator/scorer.ts, pages/Simulator/scoring.worker.ts

3computeResult opens one tally per metric per step

computeResult is the engine's entry point. It first gets the baselines for the deck size. A baseline records what a metric reads for random decks and for a sorted deck, and section 7 uses it to turn readings into levels. The sizes the site offers (99, 60, and 52) have stored baselines. Any other size is calibrated on the spot from 40 batches and kept for the rest of the visit.

It then opens a batch for every metric at every step. A batch is a running tally: you add decks to it one at a time and ask it for one number at the end. A routine of 11 moves has 12 steps (the starting deck plus one after each move), so it opens 4 × 12 = 48 batches.

Files: engine/simulate.ts, engine/calibrate.ts, engine/baselines.ts

4dealRuns puts 1,200 decks through the routine

dealRuns deals a fresh starting deck, shows it to the metrics, and then does each move in turn, showing the deck to the metrics after every move. It repeats that for 1,200 decks. Each deck finishes its routine before the next one is dealt, so the random numbers come out in the same order every time. The seeded tests rely on that order.

dealRuns doesn't measure anything itself. It calls a visit function with each deck, and computeResult supplies that function. Section 6 shows what visit does.

5Each move returns a new deck

Every move takes a deck and returns a new one. OPS maps each move name to its function.

Name in seqTokenFunctionWhat it does
mashMmashSplit the deck, then interleave the halves with riffle (diagram below).
overhandOHoverhandTake packets off the top and drop each one on the last. Packet sizes are random with an average of 3 and a limit of 8. The packets end up in reverse order.
pilePpileDeal into 6 piles in turn, each card on top of its pile, then stack the piles. It uses no random numbers, so a given deck always gives the same result.
ohrOHtohTopSplit the deck and overhand only the top half. The deck stays split.
ohbOHbohBottomSplit the deck and overhand only the bottom half. The deck stays split.
cutCcutDeckSplit the deck and put the bottom half on top.

A half overhand leaves the deck split. The deck carries the split as splitAt, the number of cards in the top half. A mash, half overhand, or cut that comes next uses that split and doesn't make its own. So OHb·OHt·M splits the deck once, overhands both halves, and mashes those same two halves, as a hand does. The overhand and the pile ignore the split. Every move except a half overhand returns a whole deck.

A move that needs a split and gets a whole deck calls cut. It picks a place from a bell curve centred on the middle of the deck, with a standard deviation of 7% of the deck, and keeps the cut inside the middle third.

How riffle interleaves two halves

The riffle is the core of the mash model. The packet sizes come from a mash the project's author measured by hand. A packet is scaled by how many cards its half still holds, so the thicker half drops faster and both halves run out at about the same time.

File: engine/moves.ts. Costs and short names are in engine/routines.ts.

6Every metric reads every deck

A metric is an object with a key, a category, a title, a trials count, a calibration, and a batch function that opens a new tally. Each time visit runs, it adds the deck to every metric's batch for that step. When all 1,200 decks are done, computeResult asks every batch for its value. The values form avg[metric][step], and that table is most of the MethodResult.

What each metric counts

Two of the metrics finish with mismatch, found in metrics/types.ts. It compares the shares a run put in each bin with the shares a random deck would put there. The result is 0 when they match and 1 when every observation lands where a random deck never puts one. Statisticians call it the total variation distance.

Two of the metrics read many parts separately (pairs of old neighbours, or starting places) and combine them with powerMean, also in metrics/types.ts. It raises each part's reading to the 4th power, averages, then takes the 4th root. A plain average would let one bad part among 99 count for a 99th of its reading. The power mean counts it for about a third, so a few bad parts aren't averaged away, while the single worst part doesn't decide the value on its own.

"Old neighbours" are cards that started next to each other: card c and card c + 1.

7Scoring turns numbers into levels

The raw values use different scales, so scoring.ts puts each one on the same scale, called a level. Level 0 is what random decks read on average, and level 1 is what a sorted deck that was never shuffled reads.

Random decks don't read exactly 0 every time. A metric counts as within noise when its level is under three standard deviations of the random readings. Order holds two metrics, neighbour order and pair order, and reads the worse of the two. Proximity and position hold one each. A category is clear only when every metric in it is within noise. The total adds up the three categories, so a sorted deck totals about 3. Distinguishability appears next to them but isn't part of the total.

The summary uses the last step. The charts use the same level function at every step.

File: engine/scoring.ts. scoreResult is in engine/simulate.ts.

8The page draws the results

When results arrive, the page builds one series for the active experiment and one for each other experiment ticked in the list: the result and its score, plus a name and a colour. The active experiment's series comes first and is drawn heaviest. The score card, the charts, and the comparison table read those series. The method list shows every experiment's total from both starting decks. The example deck doesn't use the results at all. It deals the page's starting deck through the routine once and shows the step at the caret. After an edit, it keeps the decks before the first changed move and deals only the rest again.

Files: pages/Simulator/*.tsx, components/MiniDeck.tsx, components/tracking.ts

9Two scripts run outside the browser

You run these in a terminal with Node. They use the same engine functions as the page.

npm run calibrate produces the stored baselines. For each deck size it reads 1,000 batches of 1,200 random decks, and it seeds the random numbers so the output is the same every time. It writes the results to engine/baselines.ts. Distinguishability doesn't need decks for its baseline. It uses fixed values: 50% for random and 100% for sorted.

npm run search finds the routines the home page recommends. It measures only the first and last steps, which makes each run much faster. Each stage keeps fewer routines and runs each one more times. Stage 1 deals every routine from the same 1,200 starting decks, and it races. First it reads every routine on the first 300 of those decks. walkRoutines in engine/tree.ts deals each shared prefix once, so a routine costs one more move and one measurement. Then the best 5% get a full run on all 1,200 decks. The first round only ranks the routines: on 300 decks even a random deck reads above 0, so the search doesn't print those numbers. The work runs on one worker thread per processor, and every task seeds its own random numbers, so the output doesn't depend on the number of workers.

Files: scripts/calibrate.ts, scripts/search.ts, scripts/search-worker.ts, engine/tree.ts. The options for the search are listed at the top of its file.
